> **الغرض:** هذا الملف هو المرجع الأساسي لاستكمال المشروع عبر المحادثات. عند بدء محادثة جديدة، اقرأ هذا الملف أولًا ثم راجع حالة الفرع والـ commits الفعلية قبل تنفيذ أي مهمة.

> **المستودع:** `Mhmdabbasi/bt-manager`

## 1. الرؤية النهائية

تطوير BT Manager كمنصة محلية لإدارة MikroTik، تجمع إدارة HotSpot وUser Manager، واستيراد ملفات الخدمة من الراوتر، وإدارة باقات بيع الكروت ونقاط البيع، وتصميم بطاقات الدخول وطباعتها، مع سجل محلي موثوق للدفعات والمخزون.

يجب أن تكون تجربة تصميم الكروت مستوحاة وظيفيًا من SmartCreator: محرر مرئي فعلي، لا مجرد نموذج يغيّر لونًا أو نصًا؛ مع تحكم بمقاس البطاقة، والخلفية، والعناصر النصية والمتغيرات، ومواضعها، والتنسيق، وتخطيط ورقة الطباعة، والحفظ والاسترجاع الدائمين.

## 2. متطلبات المنتج

### أ. إدارة الخدمات والراوتر
- [ ] استكمال إدارة HotSpot والتحقق من مزامنة ملفات التعريف (Profiles) وعرضها.
- [ ] استيراد ملفات User Manager وعرض Profiles وLimitations.
- [ ] إظهار القيود المرتبطة بكل Profile مع الحفاظ على علاقة many-to-many وعدم إسقاط الارتباطات.
- [ ] توضيح ما هو مستورد/موجود حاليًا على الراوتر وما هو محفوظ محليًا.
- [ ] دعم توليد كروت User Manager فعليًا بعد اكتمال التحقق من نموذج الراوتر والقيود؛ لا يُسمح باعتبار هذا مكتملًا لمجرد وجود باقات User Manager في الكتالوج.

### ب. الباقات التجارية
- [ ] إنشاء باقة كروت من داخل BT Manager وربطها بملف الخدمة الصحيح.
- [ ] حفظ سعر العميل النهائي وسعر الموزع/نقطة البيع.
- [ ] دعم بادئة عامة لكل باقة، مع تجاوز اختياري لكل نقطة بيع.
- [ ] التحقق من قواعد التوفر والأسعار والملف المرتبط قبل توليد الدفعة.

### ج. نقاط البيع والمخزون
- [ ] إدارة نقاط البيع المعتمدة (مثل البقالات والمكاتب) كجهات توزيع، وليست واجهة بيع مباشر للمستهلك بالضرورة.
- [ ] إتاحة جميع الباقات لنقطة البيع افتراضيًا أو السماح باختيار باقات محددة.
- [ ] السماح بتحديد قالب وبادئة لكل باقة عند نقطة البيع.
- [ ] تخصيص دفعات الكروت لنقطة بيع، وتسجيل حركات المخزون وتتبّع الكمية المتاحة.
- [ ] اختبار مسار التخصيص للموزع بشكل مستقل عن مسار تسجيل المبيعات؛ لا تخلط بينهما دون حاجة واضحة في تصميم المنتج.

### د. استوديو تصميم الكروت والطباعة
- [ ] محرر مرئي حقيقي للبطاقة، مع عرض فوري لما يجري تعديله.
- [ ] ضبط العرض والارتفاع بوحدات واضحة مثل mm.
- [ ] استيراد خلفية PNG/JPG/WebP، وحفظها كأصل دائم، وإعادة تحميلها عند فتح القالب لاحقًا.
- [ ] إضافة/تعديل/حذف عناصر ثابتة ومتغيرة: اسم الشبكة، اسم المستخدم، كلمة المرور، الملف/الباقة، السعر، الصلاحية، السعة، التاريخ، الرقم التسلسلي، نصوص إضافية، وغيرها حسب البيانات المتاحة.
- [ ] التحكم في موضع X/Y وحجم الخط ونوعه ولونه ومحاذاته، وإظهار/إخفاء العنصر.
- [ ] عدم افتراض أن كل متغير متوفر في كل دفعة؛ إظهار المتغيرات غير المتاحة بشكل آمن وواضح.
- [ ] تخزين تعريف التصميم وإعدادات تخطيط الصفحة في قاعدة البيانات، مع ترقيم الإصدارات.
- [ ] قالب افتراضي عام لكل باقة، مع إمكانية قالب مخصص لنقطة بيع معينة.
- [ ] تخطيط A4 يدعم عدد الأعمدة والصفوف، الهوامش، المسافات، ومقاسات البطاقة، مع معاينة قبل الطباعة.
- [ ] جعل الطباعة/الحفظ PDF متسقين مع المعاينة، وعدم طباعة عناصر واجهة التحرير.
- [ ] اختبار استمرار الأصول والقوالب بعد إعادة تشغيل التطبيق.

### هـ. سير عمل إصدار دفعة
- [ ] اختيار باقة وعدد الكروت ونقطة البيع (اختياري).
- [ ] اختيار الإعدادات العامة أو تطبيق إعدادات نقطة البيع تلقائيًا.
- [ ] استخدام قالب نقطة البيع عند وجوده، وإلا القالب العام الافتراضي.
- [ ] استخدام بادئة نقطة البيع إن كانت محددة، وإلا البادئة العامة، مع السماح بتجاوز واضح في الحالات المسموح بها.
- [ ] توليد الحسابات، حفظ بياناتها محليًا، ومعالجة حالات النجاح الجزئي بأمان.
- [ ] عرض المعاينة والطباعة وتسجيل الدفعة وحركة المخزون.
- [ ] عدم طباعة حسابات أنشئت على الراوتر ولم تُحفظ محليًا.

## 3. حالة التنفيذ المعروفة عند إعداد هذا الملف

### موجود بالفعل بحسب مراجعة الكود الأولية
- [x] قاعدة بيانات SQLite مع migrations مضمّنة في التطبيق.
- [x] أساس إدارة باقات الكروت وربطها بملفات الخدمة والأسعار والبادئة العامة.
- [x] أساس إدارة نقاط البيع وقواعد الباقات المتاحة لكل نقطة بيع.
- [x] مخطط قاعدة بيانات للأصول التصميمية `design_assets`.
- [x] مخطط للقوالب `card_templates` وإصداراتها `card_template_versions`، مع بيانات منفصلة للتصميم وتخطيط الصفحة.
- [x] منطق اختيار أحدث إصدار لقالب افتراضي عام، ودعم تجاوز قالب لنقطة البيع عبر `ResolveCardTemplateVersion`.
- [x] أساس توليد دفعات HotSpot المرتبطة بالباقة ونقطة البيع، وحفظ نسخة من بيانات الباقة والملف وقت التوليد.
- [x] أساس حفظ سجل القسائم محليًا وإرجاع الدفعات السابقة للعرض والطباعة.
- [x] مسار API لتسجيل مبيعات الباقات لنقاط البيع موجود، لكنه لا يغني عن سير عمل تخصيص دفعات الكروت للموزعين.

### نواقص مؤكدة من المراجعة الأولية
- [ ] واجهة `VoucherStudio` الحالية تعرض إعدادات محدودة للبطاقة: عنوان، عبارة إضافية، لون، خلفية، وتخطيط A4؛ لا تحقق محرر SmartCreator الكامل.
- [ ] خلفية الصورة في الواجهة تُقرأ كـ Data URL في حالة React، ولا يكفي هذا وحده لحفظ الأصل بصورة دائمة وربطه بالقالب.
- [ ] لم تظهر في المراجعة الأولية واجهات API كاملة لدورة رفع الأصول وإدارتها واسترجاعها وحفظ/تحميل القوالب؛ يجب التحقق من المستودع كاملًا قبل الجزم بعدم وجود أي أجزاء أخرى.
- [ ] التوليد في `internal/httpapi/card_vouchers.go` يرفض حاليًا توليد باقات `usermanager` برسالة أن التوليد غير متاح بعد.
- [ ] الدفعات تسجل `LimitationSnapshotJSON: "[]"` في مسار التوليد الحالي؛ يجب ألا يُعتبر حفظ قيود User Manager قد اكتمل.
- [ ] لا بد من التحقق من تناسق إعدادات القالب المحفوظة مع المعاينة والطباعة الفعلية.

### نتائج اختبار سابقة أبلغ عنها المستخدم

- `0016 - واجهة تصميم الكروت - تصميم كروت الخدش.png`: مساحة تصميم ومقاسات وعناصر قابلة للضبط.

## 5. ترتيب التنفيذ المقترح

1. **جرد تقني دقيق:** مراجعة migrations وواجهات API وطبقة التخزين والواجهة الحالية، والتأكد مما هو موجود بالفعل لتجنب إنشاء مسار مكرر.
2. **أصول التصميم والقوالب:** إكمال حفظ الأصول واسترجاعها، والتحقق من الحماية والتحقق من النوع والحجم، ثم CRUD للقوالب وإصداراتها وربطها بالباقة والنطاق العام/نقطة البيع.
3. **اختبارات التخزين وAPI:** تغطية رفع/قراءة الأصول، حفظ/تحميل القالب، حل القالب العام مقابل تجاوز نقطة البيع، وحالات عدم وجود إصدار.
4. **محرر التصميم:** بناء نموذج بيانات موحد للعناصر وخصائصها، ثم محرر مرئي ومعاينة فورية.
5. **تخطيط الطباعة:** ضبط A4 والمقاسات والهوامش والمسافات، واختبار المعاينة والطباعة/PDF.
6. **إعداد الدفعات:** تطبيق إعدادات نقطة البيع، ثم الرجوع إلى الإعدادات العامة، وحفظ إصدار القالب المستخدم مع كل دفعة.
7. **User Manager:** استكمال ربط Profiles وLimitations واختبار العلاقات، ثم تنفيذ توليد فعلي فقط بعد ضمان صحة API وسلوك الراوتر.
8. **تخصيص المخزون للموزعين:** إضافة/استكمال تخصيص دفعات إلى نقاط البيع وحركات المخزون، مع اختبارات للكمية وعدم التكرار.
9. **التحقق النهائي:** `go test ./...`، و`go vet ./...`، و`npm run typecheck`، و`npm run build`، مع توثيق ما نُفذ فعلًا.

## 6. قواعد العمل على المستودع

- العمل على الفرع `feature/phase-1-foundation` ما لم يُتفق على خلاف ذلك.
- إجراء تغييرات صغيرة ومترابطة، مع رسائل commit واضحة.
- عدم الادعاء بأن اختبارًا نجح ما لم يُشغّل فعليًا في بيئة مناسبة.
- عدم اعتبار وجود جدول أو API وحده دليلًا على اكتمال تجربة المستخدم.
- المحافظة على توافق الدفعات القديمة وإصدارات القوالب السابقة.
- تجنب حذف بيانات المستخدم أو إجراء migrations غير قابلة للتراجع دون مبرر واضح.
- عند انتهاء كل مرحلة، تحديث هذا الملف في نفس commit أو commit توثيقي قريب: حالة المهمة، الملفات المتأثرة، الاختبارات الفعلية، والقرار/الخطوة التالية.
- في بداية أي محادثة جديدة: اقرأ هذا الملف، افحص HEAD والـ diff وحالة الاختبارات، ثم واصل من أول مهمة غير مكتملة.
